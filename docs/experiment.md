# 实测：记忆阶梯在长任务中的表现

这是一次真实的 A/B 对比，目的是回答一个问题：**分层睡眠压缩到底省下了什么、代价是什么。**

## 方法

- 同一条任务提示：调查 2024 年 7 月 CrowdStrike 全球 Windows 蓝屏事件，要求 ≥8 个来源、九节结构、带来源编号。
- 同一个模型（`deepseek-flash`，窗口 1,048,576）。
- 唯一变量：**睡眠阈值**。
  - A 组：默认策略 `newestFraction = 1/3`，触发线 349,525 token。
  - B 组：`newestFraction = 0.0104`，等价于 32k 窗口的 `T/3`，触发线 10,905 token。策略公式本身没有任何改动。
- 数据来源：会话日志的 `request/header`、`compaction/*` 事件与桥接层的 token 采样。

## 结果

| 指标 | A（默认 1/3） | B（32k 等效） |
|---|---|---|
| 触发线 | 349,525 | 10,905 |
| 峰值 round token | 148,950 | 24,154 |
| 峰值总 token | 185,359 | 32,636 |
| sleep 次数 | **0** | **10** |
| 会话表面节点 | 266 | 142 |
| 耗时 | 25 分钟（被 1500 s 上限截断） | 8.7 分钟（正常结束） |
| 报告体量 | 41,027 字节 / 23 个来源 | 16,226 字节 / 10 个来源 |

## 保真度检查

拿早期轮次出现过的硬事实做保留测试：

| 事实 | A 组出现次数 | B 组出现次数 |
|---|---|---|
| `04:09` 推送时刻 | 11 | 4 ✅ |
| 850 万台受影响 | 7 | 5 ✅ |
| Channel File `291` | 11 | 5 ✅ |
| Parametrix 54 亿美元 | 5 | 3 ✅ |
| 「21 字段 vs 20 输入」错配 | 37 | 2 ⚠️ |
| Cirium 6,855 班取消 | 3 | 0 ❌ |
| 达美 3.8 亿 / 1.7 亿 | 5 | 0 ❌ |

**骨架存活，二级细节衰减。** 注意后两项在 B 组运行中本就没有抓取对应来源，不能全部归因于记忆压缩。

## 结论

- 默认 `1/3` 在 1M 窗口上等于不启用：18.5 万 token 的会话全程零压缩。这是设计意图（大窗口下不牺牲细节），但也意味着这个任务里插件没有参与。
- 真正进入压力后，压缩确实把上下文压到原来的 **1/5.7**，并且核心事实跨 10 次睡眠存活。
- 它是**容量优化**，不是质量优化。要它生效，阈值必须与模型窗口、任务量级匹配。

## 复现

```bash
# A 组（默认）
dsh --profile headless "……任务提示……"

# B 组（32k 等效）
cat > /tmp/override.yml <<'YAML'
- id: memory-ladder
  config:
    newestFraction: 0.0104
    tierCount: 6
    minTierTokens: 150
YAML
dsh --profile headless --patch /tmp/override.yml "……同一任务提示……"
```

> 注：`--patch` 是启动器参数，必须放在 profile 名之后、应用参数之前。
